ReplyCators - Change Risk Assessment & Validation Plan

QA risk analysis and test plan for three proposed changes. All findings are grounded in direct source inspection of the production codebase. No assumptions are made about unread code.

Executive Summary

Three changes are under assessment: (1) a post-import advisory toast for the Bob Working Directory, (2) exclusion of the API key from backup exports, and (3) Bob version validation in the Diagnostics CLI check. The overall risk profile is Low to Medium.

Two changes carry no risk to the critical path (extraction, execution, storage integrity): the advisory toast is purely additive UI, and the version check is a read-only Diagnostics extension. The API key export exclusion is the only change that touches a write path (the export pipeline), and its blast radius is precisely bounded and verifiable. No change touches applyImport(), the storage write path, the rollback mechanism, the Execute flow, or any content script behavior.

Highest-confidence risk identified: The API key exclusion change, if implemented incorrectly, could silently clear a user's API key on a same-machine restore from a newly-created backup. The mechanism and guard against this are explained in full in the DEPL-03 section below. This risk is verifiable, not speculative.
Second risk identified: The "What is included and excluded" table rendered in the Backup & Restore UI (line 1117, backup-restore.js) currently lists "Bob Working Directory" as "Sanitizable" with the note "Device-specific path; redacted when sanitize is on." The API key is not listed at all, even though it currently exports in unsanitized mode. All three changes require this table to be updated. Failure to update it creates a user-facing documentation lie that will mislead users about what is in their backup.

Current State Analysis

This section documents verified facts from the source that are necessary to correctly assess each change. Every statement can be traced to a specific file and line number.

Export Pipeline (backup-restore.js exportBackup())

The export pipeline has two distinct gates for sensitive data:

  1. The neverExport list (per-entry registry field) — keys listed here are never added to the keysToRead array and are therefore never read from storage. They cannot appear in the output under any circumstances.
  2. The sanitize() function (per-entry, called conditionally at line 546-548) — applies only when the user has explicitly checked "Sanitize before export." It clears fields post-read.

The bobApiKey field is inside rc:session:sf-settings which is in the exportable array. It is NOT in neverExport. The sanitize() function clears it (line 169), but sanitize is opt-in. Therefore: in a default full export, bobApiKey is present in plaintext JSON.

Import Pipeline (backup-restore.js applyImport())

The import pipeline writes only declared keys from the registry entry (lines 808-813: filteredData loop). It does not strip individual fields within a storage object — it includes or excludes the entire object. Since rc:session:sf-settings is in the exportable array and is not individually decomposed, the entire object (including all its fields) is written as a unit to storage on import.

Critical consequence: If the export path strips bobApiKey but the import path writes the full sf-settings object as-is from the backup file, a backup file that has an empty-string bobApiKey (or missing bobApiKey field) will overwrite the user's live key on same-machine restore.

Diagnostics Infrastructure (dashboard.js loadPreflightChecks)

The Diagnostics system uses lazy-cached shared promises: _getCliCheckResponse() caches the RC_PREFLIGHT_CLI_CHECK result so it is shared between checkBobCli and checkNodeRuntime (F-13 pattern). A new "Bob version" check that reads from /cli-check must use the same _getCliCheckResponse() pattern, not issue its own RC_PREFLIGHT_CLI_CHECK message. Failure to do so would break the F-13 optimization and send two HTTP requests to /cli-check per diagnostics run — a correctly identified and documented performance concern.

Settings UI Restore Path (dashboard.js syncSettingsUI)

The Bob API key is restored from storage into: (a) the module-level _committedBobApiKey variable (line 4383), (b) the DOM input (line 4391), and (c) the plugin module via onApiKeyChanged() (line 4403). The plugin module's Execute-button gating reads _bobApiKey which is seeded by onApiKeyChanged. If a restore operation writes an empty-string bobApiKey to storage, the next popup open will seed all three locations with an empty string, silently disabling Execute.

The "What is included" Table

The table in backup-restore.js render() (lines 1113-1128) is hardcoded HTML. It currently does not list the API key at all, and lists Bob Working Directory as "Sanitizable." Any change to export policy must also update this table or the UI will actively mislead users.

Proposed Change Review

Change 1: DEPL-02 - Post-Import Advisory Toast for Bob Working Directory

Precise scope

After a successful applyImport(), if the imported data contained a non-empty bobWorkingDir value inside rc:session:sf-settings, show a toast advisory: "Bob Working Directory was restored - verify the path is valid on this machine in Settings."

Touch points

  • The post-apply block in _bindUI (around line 1274 of backup-restore.js) where result.keysWritten is checked.
  • OR: a post-apply hook that reads the imported envelope's sf-settings.bobWorkingDir field.
  • app().showToast() or app().addNotification() — both are already used in the import flow.

Risk analysis

  • Risk: reading a nested field from the envelope for the toast condition. The toast must read envelope.sections['com.replycators.salesforce-extractor']['rc:session:sf-settings']?.bobWorkingDir. This is a nullable chain through several layers. If any level is absent (e.g., a selected-mode export that didn't include the SF plugin, or a backup from before bobWorkingDir was added to the schema), the access must not throw. Must be null-safe throughout.
  • Risk: toast fires on every import, not just cross-machine restores. A same-machine backup-and-restore will also show the advisory toast, which is technically correct but mildly annoying. Accept this: the alternative (detecting "same machine" by path comparison) is overengineering for a toast.
  • Risk: keep-existing strategy. If the user selects "Keep existing on conflict" and the sf-settings key already exists on the current machine, the key is excluded from writes. The toast must not fire in this case, because nothing was actually written. The condition should check whether the sf-settings key is in result.keysWritten OR the final write plan, not just whether the envelope contains it.
  • No risk to storage integrity, rollback, or the Execute path. This is purely additive UI after a successful write. The worst-case failure mode is: toast does not appear, or appears when it should not. Neither causes data loss.

Adjacent feature impact

None. The toast uses the existing addNotification() platform API. No storage key, schema, or import engine changes.

Change 2: DEPL-03 - Exclude API Key from Backup Exports

Precise scope

Strip bobApiKey from the rc:session:sf-settings object in the export output, in all export modes (full, selected, sanitized, unsanitized). The import pipeline and storage schema are unchanged.

Critical design question that must be resolved before implementation:
The export currently exports the entire rc:session:sf-settings object as an atomic unit. The import path writes it back as an atomic unit. If the export strips bobApiKey from the object and the user restores that backup on the same machine, the import writes an sf-settings object that has no bobApiKey field (or an empty string). This will clear the user's live API key.

This is not a theoretical edge case. It is the normal same-machine backup-restore flow.

Two valid implementation approaches — they have different risk profiles

Approach A — Strip from export, accept that import may clear the key: Document explicitly that after importing a backup, the API key must be re-entered. Add the post-import advisory from DEPL-02 to also cover the API key. This is the simplest implementation but imposes friction on same-machine restores.

Approach B — Strip from export, teach the import pipeline to preserve the key: Before writing the sf-settings object, merge: read the live bobApiKey from current storage, re-inject it into the imported object before writing. This requires a targeted change to applyImport() or a new pre-write merge step specifically for credential fields. Higher complexity, but preserves the user's key on same-machine restores.

Approach B touches applyImport() — the most safety-critical function in the entire plugin. The rollback mechanism, read-back verification, and import lock all depend on this function operating exactly as designed. Any modification to its write plan construction carries regression risk for ALL plugins, not just Salesforce. Approach B is therefore rated as Higher Risk.

Recommendation: Approach A with enhanced post-import advisory

Approach A is safer, contained, and honest about the trade-off. The advisory toast must cover both the working directory AND the API key. The "What is included" table must list the API key as "Never exported." The sanitize function's existing bobApiKey = '' line becomes redundant but harmless — leave it in place.

Additional risk: the _sanitized flag in the envelope

The envelope includes _sanitized: sanitize (line 563). After this change, an unsanitized export will nonetheless have an empty bobApiKey. A consumer reading _sanitized: false and expecting to find a key may be surprised. This is a documentation concern, not a functional risk, but it must be noted in the changelog and any API documentation.

Adjacent feature impact

  • The "What is included" table: Must add a row for "BobShell 2.0 API key" as "Never exported" and update the "Bob Working Directory" row note.
  • The sanitize description text in the export UI (line 1020): references "working directory paths" — add "API keys" to this description.
  • The sensitiveFields array in the registry entry (lines 135-139) already lists 'rc:session:sf-settings.bobApiKey'. This field is documentation-only (not used by any logic in the current codebase). It remains accurate after the change.
  • No impact on the import pipeline if Approach A is used.

Change 3: Bob Version Validation in /cli-check and Diagnostics

Precise scope

Add a bobVersionOk boolean and optional bobVersionWarning string to the /cli-check HTTP response. Add a new Diagnostics check item (or extend checkBobCli) that evaluates bobVersionOk and renders a "warn" status if the detected major version is below the minimum.

F-13 shared promise constraint — verified critical dependency

Verified: checkBobCli and checkNodeRuntime both call _getCliCheckResponse() (lines 2790 and 2834). This shared lazy promise is used to avoid two separate RC_PREFLIGHT_CLI_CHECK background messages per diagnostics run. A new version check function MUST also use _getCliCheckResponse(). If implemented as a new standalone check function that calls chrome.runtime.sendMessage({ type: 'RC_PREFLIGHT_CLI_CHECK' }, ...) directly, it will break the F-13 optimization and issue a redundant background HTTP request. This is not a minor issue — the background message handler has a 4-second AbortController timeout, so a doubled request means doubled network latency risk.

GROUPS array modification — verified critical dependency

The new check must be added to the GROUPS['LocalRuntime'].checks array (line 3018). The allPromises and promiseGroupMap parallel arrays are built from this configuration. Adding a check to the array is safe as long as the check returns a Promise that always resolves (never rejects), which is the contract for all existing checks. A check that can reject would cause Promise.allSettled to catch it and render a generic error card — acceptable behavior, but the check should resolve with a safe error descriptor instead.

Bob 1.0 mode cross-dependency — verified

The bobUseBob1 setting is stored in rc:session:sf-settings and is read during startup into _restoredSfSettings. The Diagnostics system does not currently read bobUseBob1. If the version check issues a "Bob 2.x required" warning for a user who has explicitly configured Bob 1.0 mode, the warning is misleading and will erode trust in the Diagnostics panel. The version check must read rc:session:sf-settings.bobUseBob1 and suppress or reframe the warning accordingly.

The sfEnabled guard — verified pattern

All SF-related diagnostics checks begin with if (!sfEnabled) { resolve({ status: 'skip', ... }); return; }. The new check must follow this pattern identically. sfEnabled is already in scope within loadPreflightChecks().

Version string parsing risk — verified from server source

The server currently validates the version string with /^[\w.\-+\s]{1,80}$/ (line 357 of bob-helper-server.js). This regex accepts a wide range of formats including multi-word strings like "BobShell 2.0.1 (build 123)". Any numeric comparison against this string must handle the case where it does not begin with a plain digit. The Node runtime check in checkNodeRuntime (line 2854) uses /^[\d.]+$/.test(response.nodeVersion) as a pre-check before numeric parsing — the Bob version check should use an analogous guard before attempting major version extraction.

Adjacent feature impact

  • The /cli-check HTTP response schema gains new fields. This is additive and backward compatible. All existing consumers of the response (the Settings Working Directory Save button path, checkBobCli, checkNodeRuntime) only read the fields they expect and ignore unknown ones.
  • The Diagnostics "Local Runtime" group gains one additional check card. No layout breakage expected.
  • The Bob helper server gains a synchronous comparison operation — no event-loop impact.

Validation & Test Plan

All test cases are designed to be runnable manually in a development instance of the extension with the browser DevTools open. No automated test infrastructure is assumed to exist (per AGENTS.md §26).

Pre-conditions for all tests

  • Extension loaded from root directory in Edge developer mode.
  • Bob Helper server running at port 47123 with a valid BobShell installation.
  • A known API key configured and saved in Settings - Salesforce Case Extractor.
  • A valid Bob Working Directory configured and saved.
  • Activity Log visible for side-effect inspection.
