Bob Helper - Temp File Architecture Analysis

Technical Design Review · tools/bob-helper-server.js · tools/bob-launcher-template.ps1 · ReplyCators v1.45.6

Executive Summary

Current design is architecturally correct but partially incomplete in its lifecycle management. The files are functionally required as the inter-process communication (IPC) channel between the Node.js HTTP server and the detached PowerShell launcher. The system already implements a multi-layer cleanup strategy (lock-file protocol, startup eviction, graceful shutdown eviction), but that cleanup is deferred - files are visible in the user's working directory during and briefly after execution, which creates the user experience concern being raised. The proposed solution (immediate deletion after successful processing) is sound in principle, but requires precision in timing to avoid a race condition with the launcher reading the prompt file.

The core tension is between two legitimate needs: the launcher must read the .txt prompt file before it can be deleted, and the user wants the file gone immediately. The existing lock-file protocol (.lock companion) was designed to solve exactly this race - it just does not currently drive a post-completion active cleanup pass. Implementing that final step (deleting the .txt and .status.json after the launcher signals completion) resolves the UX concern without sacrificing reliability.

Current Behavior Analysis

Why the Files Exist

The fundamental constraint is that MV3 browser extensions cannot spawn native processes. The Chrome/Edge service worker can only perform network requests. IBM Bob is a CLI tool. The gap between these two worlds is bridged by bob-helper-server.js, a local Node.js HTTP server. When the user clicks Execute:

1
Plugin sends RC_EXECUTE_BOB (chrome.runtime.sendMessage)
2
background.js relays via HTTP POST to http://127.0.0.1:47123/execute
3
Server writes <requestId>.txt (prompt), <requestId>.lock, and <requestId>.status.json to disk
4
Server spawns powershell.exe with RC_PROMPT_FILE env var pointing to the .txt file (detached: true, fire-and-forget)
5
Server immediately returns {ok: true} - it has NO pipe to the launcher
6
Launcher reads RC_PROMPT_FILE, deletes .lock, executes Bob (Bob version-aware: v1 via stdin pipe, v2 via -p flag)
7
Launcher updates .status.json at each state transition (pending -> running -> completed/failed)
8
.txt and .status.json remain on disk - no active deletion after completion
The file is the IPC channel. The server and launcher share no stdin/stdout pipe - the prompt must be written to disk so the detached PowerShell process can read it.

Three Artifact Files Per Execution

The question identifies two files, but the actual count is three:

FilePurposeLifecycle OwnerCurrent Fate
<requestId>.txt Assembled Bob prompt - the IPC payload. Read by the PowerShell launcher via Get-Content -Raw. Server writes; Launcher reads Deleted at startup (24h eviction) or server shutdown. NOT deleted after use.
<requestId>.lock Signals the launcher has not yet consumed the prompt. Deleted by launcher immediately after reading the .txt. Server writes; Launcher deletes Short-lived by design - gone once launcher reads the prompt. Usually invisible to user.
<requestId>.status.json Execution lifecycle state (pending/running/completed/failed). Read by GET /status/:requestId polling from the plugin. Server writes initial state; Launcher updates state Deleted at startup (24h eviction) or server shutdown. NOT deleted after use.

Existing Cleanup Mechanisms (Already Implemented)

MechanismTriggerScopeLimitation
Age-based eviction Server startup (cleanupOldTempFiles) Files > 24h in TEMP_ROOT Does not clean working-directory-relative files. No cleanup for files less than 24h old.
Graceful shutdown SIGINT / SIGTERM / process.exit (cleanupAllTempFiles) All tracked dirs, lock-aware Only fires if the server is gracefully stopped. Kill or crash leaves files behind.
Lock-file protocol Launcher deletes .lock after reading .txt Prevents cleanup from removing unconsumed prompts Cleanup is only triggered at startup/shutdown, not on lock deletion.

Root Cause of the User Experience Problem

When a working directory is configured, files are written directly into the user's project/workspace folder rather than into %TEMP%\replycators-bob-helper\. This means prompt files appear in the user's codebase, which is more noticeable and more objectionable than files appearing in a hidden system temp directory.

The gap is specifically: the lock deletion by the launcher is a perfect signal that the file is safe to delete, but nothing in the current codebase acts on that signal to trigger immediate deletion of the .txt and .status.json.

Evaluation of Proposed Solution

Proposed: keep files hidden from user, automatically delete them immediately after successful processing.

Advantages

  • Eliminates user-visible clutter in the working directory - the primary UX complaint is resolved.
  • Reduces attack surface - prompt files may contain case data, user instructions, or API context. The shorter their on-disk lifespan, the lower the exposure window.
  • Aligns with the lock-file protocol's intent - the protocol already designates the lock deletion as the safe-to-delete signal. This change just adds the action that should follow that signal.
  • No change to the IPC mechanism - the fundamental architecture is preserved. Files are still created and read exactly as before.
  • Low implementation risk - the signal already exists; the only missing piece is a cleanup action triggered by it.

Disadvantages

  • "Immediately after successful processing" is ambiguous. If interpreted as "delete as soon as Bob finishes," this requires the launcher to perform deletion - but the launcher today only updates the .status.json and exits. Adding file deletion to a fire-and-forget script increases coupling between the launcher and the server's file layout.
  • Status file dilemma. The .status.json is still being polled by the plugin every 3 seconds via RC_BOB_STATUS. Deleting it immediately after Bob completes creates a race: the final poll might arrive after deletion, returning 404 and incorrectly treating the execution as lost.
  • Reduces post-failure diagnostics. If Bob exits with a non-zero code, the prompt file may be the only artifact that captures exactly what was sent. Deleting it immediately on success still leaves it on failure - which is good - but "successful processing" must be carefully defined to mean "Bob exited 0 and status was confirmed."
  • Does not help the TEMP_ROOT case independently. Files in %TEMP%\replycators-bob-helper\ (no working directory configured) are less visible to the user but still persist until the 24h eviction at next startup. The proposed solution should address both locations.

Risks

RiskSeverityMitigation
Status poll arrives after deletion - 404 misread as failure Medium Server should cache the final status in memory for a TTL (e.g. 30s) after file deletion, serving it from the in-memory cache.
Launcher deletes file before Bob has fully consumed it (Bob 1.0 stdin-pipe path) High On the Bob 1.0 path, the prompt is piped via stdin ($promptContent | & bob.ps1). The file content is read into $promptContent first, then piped. Deletion after the read but before Bob exits is safe.
Concurrent executions - one cleanup deletes another request's file Low Each request has a unique requestId-based filename. Cleanup is per-file, not directory-wide.
Server crash during Bob execution - no cleanup path fires Medium Startup-eviction (24h) remains as the backstop. For working-directory files, this is the only safety net if the server is killed.
File deleted before diagnostic investigation completes Low Only applies to success-path deletion. Failure path should always retain files. DEBUG=1 mode could optionally retain all files.

Alternative Solutions

Ranked from most to least recommended.

1 Post-Completion Active Cleanup Triggered by Lock Deletion
Recommended Complexity: Low

The launcher already deletes the .lock file when it has consumed the prompt. Extend the launcher to also delete the .txt file immediately after reading it (when $promptContent is populated). Add a deferred deletion of the .status.json to the launcher after writing the final completed or failed state, with a 10-second delay to allow the plugin's polling to catch the final status before the file disappears. The server's in-memory _usedPromptDirs set already tracks all relevant directories - extend it to also track per-request metadata for a short-lived in-memory status cache so that post-deletion polls do not 404.

Pros

  • Files disappear from working directory within seconds of execution start
  • Exploits existing lock-file protocol signal without new infrastructure
  • Handles both TEMP_ROOT and working-directory-relative files
  • No change to IPC mechanism - file is still written and read identically
  • Low risk - launcher already performs Remove-LockFile; same pattern extended to .txt
  • Failure path retains files (only success-path deletion for .txt)

Cons

  • Requires small in-memory status cache in server to handle late polls
  • Status file deletion delay (10s) means files are not completely gone instantly
  • Launcher script grows slightly more complex

agents.md alignment: Fully compliant. No new storage keys, no new platform dependencies, no changes to dashboard.js or the plugin manifest. Touches only tools/ files. Does not introduce automated tests. Follows the lock-file protocol design intent.

2 Write All Files Exclusively to TEMP_ROOT (Never to Working Directory)
Partial Fix Complexity: Low

Change resolvePromptDir() to always use TEMP_ROOT regardless of workingDir. Pass workingDir to the launcher only for Bob's --include-directories context, not as the file location. This isolates all temp files to %TEMP%\replycators-bob-helper\ which is a system folder users rarely browse.

Pros

  • Eliminates working-directory clutter immediately with a one-line change
  • No race conditions or timing changes
  • TEMP_ROOT already has 24h eviction at startup

Cons

  • Files still persist until 24h eviction - just in a less visible location
  • Does not address the 24h persistence gap or the security concern
  • If TEMP path differs from workingDir across drives, no functional impact on Bob - working dir is still set correctly via Set-Location

agents.md alignment: Compliant. This is a pure tools/ layer change. Could be implemented alongside Alternative 1 as a belt-and-suspenders measure.

3 Named Pipe / stdin Pass-Through (Eliminate Files Entirely)
Long-term Complexity: High

Replace file-based IPC with a Windows Named Pipe. The server opens a named pipe server (\\.\pipe\replycators-bob-<requestId>), writes the prompt, and the launcher reads from the pipe. No temp files are created. Bob 1.0 could pipe prompt directly; Bob 2.0 would need a temp file only for the -p flag inline-prompt path or a short-lived pipe-to-string read.

Pros

  • Zero file system footprint - completely eliminates the UX and security concerns
  • More architecturally clean IPC for a production-grade tool
  • No eviction logic needed

Cons

  • Named pipe creation in PowerShell requires .NET/System.IO.Pipes - more complex launcher
  • Bob 2.0's -p flag takes the prompt as a command-line argument (not stdin), so a file or a very long argument string is still required for that path
  • High complexity with limited marginal benefit over Alternative 1
  • Named pipes on Windows have known complexity around connection timing
  • Requires thorough testing across Bob 1.x and Bob 2.x invocation paths

agents.md alignment: Compliant in principle, but constitutes a significant architectural change to the IPC layer. Would require an ADR and MINOR version bump. Deferred until after RC-015 Phase 2 per the Long-Term Architecture Direction.

4 Reduce Eviction Threshold (1h Instead of 24h)
Insufficient Complexity: Low

Change OLD_FILE_MAX_AGE_MS from 24 hours to 1 hour. Files would still be cleaned up on the next server startup, which may be hours or days later. The user-visible clutter during active use is not addressed at all. Not recommended as a primary fix.

Pros

  • One-line change - zero risk

Cons

  • Does not address the problem - files still appear during active use
  • Does not help working-directory-relative files which are not in TEMP_ROOT

agents.md alignment: Compliant but insufficient. Purely cosmetic improvement.

Recommended Approach

Implement Alternative 1 (post-completion active cleanup) combined with Alternative 2 (TEMP_ROOT isolation).

The two changes are complementary and neither is sufficient alone: Alternative 2 immediately eliminates working-directory clutter without any timing risk, while Alternative 1 ensures the files are actively deleted rather than accumulating in TEMP_ROOT until the next startup.

Specific Implementation

  1. In bob-launcher-template.ps1: After $promptContent = Get-Content -Path $env:RC_PROMPT_FILE -Raw -Encoding UTF8 and the Remove-LockFile call - add an immediate deletion of the .txt file. The content is already in memory; the file is no longer needed.
  2. In bob-launcher-template.ps1: After writing the final completed or failed status, add a deferred cleanup of the .status.json (via a Start-Sleep 15; Remove-Item background job, or simply delete it immediately and accept that a very late poll will get a 404 - which the plugin already handles gracefully by stopping polling on any terminal state).
  3. In bob-helper-server.js: Add a lightweight in-memory status cache (Map<requestId, statusObject>) that stores the last known status object for each completed/failed request. Keep entries for 60 seconds, then evict. The readStatusFile() function falls back to this cache on file-not-found, so late polls after file deletion still return the correct final state.
  4. In bob-helper-server.js: Change resolvePromptDir() to always return TEMP_ROOT, passing workingDir only as RC_WORKING_DIR for Bob's execution context (Set-Location), not for file placement. This is a one-line change to the if (!workingDir) return TEMP_ROOT condition.

Migration Plan

Step 1
Change resolvePromptDir() to always return TEMP_ROOT
In bob-helper-server.js, simplify resolvePromptDir(workingDir) to unconditionally return TEMP_ROOT. The _usedPromptDirs tracking set becomes TEMP_ROOT-only. Ensure ensureTempRoot() is always called. The workingDir value continues to be passed to the launcher as RC_WORKING_DIR unchanged. Risk: None. Working directory is used by the launcher for Set-Location and --include-directories, not for file placement.
Step 2
Add .txt deletion to launcher after prompt read
In bob-launcher-template.ps1, immediately after the Remove-LockFile call, add: try { Remove-Item -Path $env:RC_PROMPT_FILE -Force -ErrorAction SilentlyContinue } catch {}. The content is already captured in $promptContent. This makes the file's existence ephemeral - gone within milliseconds of the launcher starting.
Step 3
Add in-memory status cache to server
In bob-helper-server.js, add a Map named _statusCache. When readStatusFile() cannot find a file, check the cache. In writeStatusFile(), when the state is completed or failed, also write to the in-memory cache with a TTL timestamp. Add a periodic setInterval eviction (every 60s) to remove entries older than 120s. This ensures late status polls after file deletion still return the final state.
Step 4
Add .status.json deletion to launcher after writing final state
In bob-launcher-template.ps1, in both the success and failure paths, after the final Write-BobStatus call, add: Start-Sleep -Seconds 20; try { Remove-Item -Path $env:RC_STATUS_FILE -Force -ErrorAction SilentlyContinue } catch {}. The 20-second delay allows any in-flight status polls to complete before the file disappears. The in-memory cache (Step 3) handles any polls that arrive after deletion.
Step 5
Update error handler in launcher
In the catch block of bob-launcher-template.ps1, do NOT delete the .txt or .status.json on failure. Retain them for diagnostic investigation. The last-error.log file in TEMP is also retained. This preserves the current excellent failure-mode observability.
Step 6
Update documentation
Update docs/BOB-HELPER-SERVER.md Temp file lifecycle section to reflect: files written to TEMP_ROOT only; .txt deleted immediately after prompt read; .status.json deleted ~20s after final state write; in-memory cache provides 120s coverage for late polls. Update the Execution Flow numbered list (step 14). Version bump to PATCH in relevant plugin and platform versions.
Step 7
Update CHANGELOG.md and dist/ mirror
Following agents.md §12: bump platform PATCH version, update all Authoritative Version Locations, copy modified root files to dist/.

Edge Cases and Failure Scenarios

ScenarioCurrent BehaviorBehavior After Recommended Changes
Server crashes mid-execution Files remain until next startup eviction (24h) Same - server crash cannot trigger file cleanup. Launcher continues to run independently and now self-cleans its own files on completion.
Launcher crashes before reading prompt .lock and .txt remain; evicted after 24h Same. .lock ensures the file won't be evicted prematurely if server restarts before 24h. After 24h, age-based eviction fires.
Concurrent executions Unique requestId per execution - no filename collision Same. Each execution has its own .txt and .status.json. Cleanup is per-file.
Late status poll after file deletion Returns 404 - plugin stops polling (currently treated as failure) In-memory cache serves the final state for 120s after deletion. 404 only possible after 120s TTL expiry, which is well outside the polling window (3s interval, ~10 polls max).
Retry / re-execute same request New requestId generated - no collision Same. Each Execute click generates a new requestId via 'sf-' + Date.now() + '-' + random.
Bob exits non-zero (partial failure) Files retained until eviction .txt is still deleted (already read before Bob ran). .status.json is retained indefinitely on failure path (no deferred deletion added to catch block). last-error.log is always written.
Working directory configured by user Files written INTO the user's project directory - visible in file explorer / IDE Files written to TEMP_ROOT only. User's project directory remains clean.
Server restart while Bob is running cleanupAllTempFiles() at shutdown respects .lock protocol Same. If launcher already deleted the .txt (Step 2), the shutdown cleanup finds nothing to do for that file. .status.json is still present and will be cleaned by shutdown.
Disk write failure (TEMP not writable) Server returns 500 "Failed to write prompt file" Same - the bob-helper.ps1 check (CHECK 5) validates TEMP writeability as a pre-flight check.
Diagnostic investigation of a problem Developer enables REPLYCATORS_BOB_HELPER_DEBUG=1 to see logs; files persist For failures: .status.json is retained (no deferred cleanup on failure path). For successes: files are cleaned. Consider adding a DEBUG mode that suppresses file cleanup entirely for deep investigation.

  • No new platform logging or notification systems introduced

Final Verdict

Implemented with modifications.

The proposed solution ("delete files immediately after successful processing") is correct in intent but requires two modifications to be safe and complete:

  1. Add an in-memory status cache to the server before deleting the .status.json. Without it, deleting the status file while the plugin is still polling creates a window where the plugin receives a 404 and may incorrectly surface an error to the user despite the execution succeeding.
  2. Scope temp file placement to TEMP_ROOT exclusively. The UX problem is worst when files appear in the user's working directory. Isolating all temp files to %TEMP%\replycators-bob-helper\ addresses the most visible manifestation immediately and is a zero-risk change independent of the timing work.

The recommended implementation (Alternatives 1 + 2 combined) achieves all stated goals - files are hidden from the user's project directory, actively deleted within seconds of use, and the diagnostic and failure-recovery properties of the current design are fully preserved. The lock-file protocol, the status-file polling loop, the 24h backstop eviction, and the graceful-shutdown cleanup all remain intact and complementary.

The named-pipe alternative (Alternative 3) represents a cleaner long-term architecture and should be noted in the Technical Debt Register for consideration during RC-015 Phase 2, but it is disproportionate to the current problem and should not block the near-term fix.
